一、问题一句话

私有可写 VMA 做扩张式 mremap 搬移时，若页表搬移中途失败（ENOMEM），内核会把数据完整回退到旧 VMA——进程状态恢复原样，但全局 Committed_AS 从此多记了扩张增量（delta）页，且永远不会被纠正，直到系统重启。这不是内存泄漏（物理页没丢），而是记账泄漏：在 overcommit 策略下，它会让长期运行的服务器越来越早地拒绝合法的内存申请。

二、背景知识：Committed_AS 与它的两条调用链

2.1 overcommit 与"承诺记账"

Linux 允许进程申请超过物理内存 + swap 总量的虚拟内存（overcommit），策略由 /proc/sys/vm/overcommit_memory 决定：模式 0（默认，heuristic）、模式 1（always）、模式 2（strict，承诺和不得超过 CommitLimit）。支撑判断的核心计数器是 Committed_AS——内核变量 vm_committed_as（mm/util.c:922，percpu_counter 类型），表示"如果所有进程都把申请到的虚拟内存写满，最多需要多少物理内存 + swap"。

类比：Committed_AS 是银行批出去的授信总额。这个 BUG 的效果是——某笔授信被批准后业务撤销了，授信额度却忘了收回，银行从此以为自己放出去的钱比实际多。

2.2 记账链（charge）：一笔账怎么加进去

只有私有可写映射（VMA 带 VM_ACCOUNT）记账。mmap/brk/mremap 扩张时走下面这条链——先加账、再判定，判定不过就自己减回去：

调用方（mmap/brk/mremap）
  └─ security_vm_enough_memory_mm()              security/security.c:735   [LSM 总入口]
      └─ cap_vm_enough_memory()                  security/commoncap.c:1453  [LSM 钩子，决定 cap_sys_admin]
          └─ __vm_enough_memory()                mm/util.c:959             [真正的策略判定]
              ├─ vm_acct_memory(pages)           include/linux/mman.h:76    [先加账！]
              │    └─ percpu_counter_add_batch(&vm_committed_as, ...)   vm_committed_as 定义于 mm/util.c:922
              ├─ 判定 overcommit_memory 三种模式：
              │    ├─ ALWAYS(1) → return 0（永不拒绝）
              │    ├─ GUESS(0)  → 粗略检查后 return 0 / goto error
              │    └─ STRICT(2) → percpu_counter_read_positive(&vm_committed_as) < allowed ?
              └─ error:（拒绝时）
                   └─ vm_unacct_memory(pages)   mm/util.c:999 / include/linux/mman.h:81  [自己减回去]
                       └─ vm_acct_memory(-pages)

注意 vm_acct_memory() 与 vm_unacct_memory() 都是 include/linux/mman.h 里的 inline 函数（76/81 行）——加账与减账最终都落到同一个 percpu_counter。任何调用方拿到"允许"返回后，这笔账就只存在于全局计数器里，唯一的冲销依据是 VMA 销毁路径。

2.3 冲账链（uncharge）：账怎么减回来

VMA 销毁时统一走 munmap 通道，冲账数额由 vms->nr_accounted 汇总，而汇总的条件就是 VMA 上的 VM_ACCOUNT 标志——这正是全案的钥匙：

munmap / 进程退出 / 内核内部 do_vmi_munmap
  └─ do_vmi_munmap()                            mm/vma.c:1710
      ├─ vms_gather_munmap_area()               mm/vma.c:1546  ★关键：只有带 VM_ACCOUNT 的 VMA 才累计
      │    └─ if (vma_test(next, VMA_ACCOUNT_BIT))
      │           vms->nr_accounted += nrpages;  /* 没这个标志的 VMA，页数不计入 */
      └─ vms_complete_munmap_vmas()             mm/vma.c:1410
          ├─ remove_vma(vma)                    逐个销毁 VMA（mm/vma.c:1441）
          └─ vm_unacct_memory(vms->nr_accounted) mm/vma.c:1443  [实际冲账点]

进程退出（另一入口）：
  exit_mm() → exit_mmap()                       mm/mmap.c:1288
  └─ vm_unacct_memory(nr_accounted)             mm/mmap.c:1341  [同样按 VMA 的 VM_ACCOUNT 汇总]

结构性缺陷：记账动作（2.2 链，写全局计数器）与冲账依据（2.3 链，读 VMA 标志）是两套独立机制。只要某个 charge 发生后，对应 VMA 在冲账时刻恰好不带 VM_ACCOUNT，这笔账就变成无人认领的"裸账"。mremap 错误路径恰好制造了这个组合——这就是 BUG 藏身 20 年的结构原因。

步骤 ①：charge delta — vrm_calc_charge()

泄漏闭环：① 步 vrm_calc_charge() 记入的 delta（经由 security_vm_enough_memory_mm() 落进 vm_committed_as）→ ⑤ 步清标志导致 unmap 冲账 0 页 → vrm->charged 暂存的数值再无人使用（整个函数只剩 mremap.c:1280 一处消费它）。对照代码里 v7.1 重构特意造了 charge/uncharge 配对，说明作者知道"失败要退账"，唯独漏了这条路径。

四、四条路径总账推演（含调用链对照）

设旧 VMA 记账 O 页，扩张量 D 页。对四条路径做守恒检查：

mremap 扩张搬移四路径的 Committed_AS 总账（O = 旧账，D = delta）
路径调用链走向关键动作结束时账目结论
正常成功 move_vma → copy_vma_and_data → move_page_tables 全程成功 → unmap_source_vma ① charge +D（mremap.c:1376）→ 新 VMA 接管 O+D → ⑤ 清标志 unmap 旧 VMA 冲 0，但新 VMA 持有 O+D O + D（新 VMA 实际持有） 守恒 ✓
② copy_vma 失败 move_vma → copy_vma_and_data → copy_vma 失败 → vrm_uncharge()（mremap.c:1280） ① charge +D → ② 失败 → vm_unacct_memory(D) 冲回 O 守恒 ✓
DONTUNMAP 失败 move_vma → copy_vma_and_data 失败 → unmap_source_vma（accountable_move=false 不清标志） ① charge 全量 new_len → ⑤ 不清 VMA_ACCOUNT → do_vmi_munmap 冲 new_len（mm/vma.c:1443） O 守恒 ✓
③ 中途失败 move_vma → copy_vma_and_data → move_page_tables ENOMEM → pmc_revert 回退 → unmap_source_vma 清标志 unmap ① charge +D → ④ 数据回退旧 VMA → ⑤ 清标志（mremap.c:1198）→ 冲账 0 页 O + D，实际仅 O 在用 泄漏 D ✗

三条对照路径全部守恒的事实说明：这不是"错误路径本来就该有损耗"，而是唯独中途失败路径漏了退账。尤其对比②和③——②在同一个 copy_vma_and_data() 函数里正确退账，③只是把失败时机推迟到了搬页表阶段，待遇却截然不同。

为什么进程退出也救不回来：退出冲账走 exit_mmap()（mm/mmap.c:1288）→ vm_unacct_memory(nr_accounted)（mm/mmap.c:1341），依据仍是 VMA 的 VM_ACCOUNT。这笔 D 页的账早已与任何 VMA 脱钩，无人替它冲账。唯一清除手段是重启。后果画像：默认 heuristic 模式下，长跑服务器"越用越紧、重启就好"的诡异症状。

五、根因与 20 年历史

git log -S 'Conceal VM_ACCOUNT' -- mm/mremap.c 追溯到 1da177e4c3f4（Linux-2.6.12-rc2，2005 年）——内核 git 仓库第一个提交，原注释保留至今：

/* Conceal VM_ACCOUNT so old reservation is not undone */
if (vm_flags & VM_ACCOUNT && !(flags & MREMAP_DONTUNMAP))
	vma_clear_flags(vma, VM_ACCOUNT);

2005 年的这行动作（如今位于 unmap_source_vma()，mremap.c:1197-1198）保护的对象至今正确；但没人意识到它同时让 delta 电荷成了孤儿。2025 年 v7.1 的 vrm 重构（b714ccb02a76）引入了 vrm_calc_charge()/vrm_uncharge() 配对（mremap.c:984/:1013）——说明重构者意识到"charge 需要退账"，却只在 copy_vma 失败分支（mremap.c:1280）用了一次。

为什么 20 年无人发现

  • 触发条件苛刻：私有可写 VMA + 扩张搬移 + 页表分配恰好在搬移窗口内失败，三重低概率叠加；
  • 后果是保守方向：多记账只会更早拒绝内存申请，不崩溃不丢数据，监控上表现为"Committed_AS 缓慢爬升"，极易误读为业务自然增长；
  • 重启即愈：掩盖长周期累积效应；
  • 静态工具盲区：锁/引用计数检查器不覆盖"计数器 ↔ VMA 标志跨对象守恒"，只有人工做总账推演才能看见。

六、复现方法论：fault injection 精确打点

复现难点是让 move_page_tables() 恰好在 mremap 执行窗口内失败——自然 OOM 不可控（可能失败在 charge 阶段，那条路径不泄漏）。方案：内核自带 fail_page_alloc，打点即 3 步链路图中的 should_fail_alloc_page()（mm/fail_page_alloc.c:26）。

6.1 make-it-fail 判定链（为什么只打 demo 进程）

demo 写 /proc/self/make-it-fail = 1          fs/proc/base.c:3359  [proc 文件注册]
└─ current->make_it_fail = 1                   /* 任务结构体上的开关 */

mremap 窗口内第一次页分配：
should_fail_alloc_page()                       mm/fail_page_alloc.c:26
└─ should_fail_ex(&fail_page_alloc.attr, ...)  lib/fault-inject.c:124
    ├─ if (attr->task_filter && !fail_task(attr, current))
    │    return false                          /* task_filter=1 时：非 make-it-fail 任务全部放行 */
    │    fail_task()                            lib/fault-inject.c:79  [return in_task() && task->make_it_fail]
    ├─ times/space/interval/probability 判定
    └─ return true → __alloc_frozen_pages_noprof 返回 NULL → 页表分配失败

demo 在 mremap 系统调用前后开关 make-it-fail（写 1 / 写 0），把失败精确圈定在单次系统调用内。mremap(FIXED) 主路径在 move_page_tables() 之前没有任何页分配（VMA 结构走 slab、charge 是纯计数），所以窗口内第一次 __alloc_pages 必然是 dst 页表分配——注入命中即产生"中途失败"形态。

6.2 两个必踩的默认值坑（源码实证）

mm/fail_page_alloc.c:7-18 的静态初始化，两个默认值会让 naive 配置一枪不中：

static struct {
	struct fault_attr attr;
	bool ignore_gfp_highmem;
	bool ignore_gfp_reclaim;
	u32 min_order;
} fail_page_alloc = {
	.ignore_gfp_reclaim = true,   /* 坑1：带 __GFP_DIRECT_RECLAIM 的分配默认不注入 */
	.ignore_gfp_highmem = true,
	.min_order = 1,               /* 坑2：order-0 分配默认不注入！页表恰恰是 order-0 */
};
  • 坑 1：页表分配 GFP_PGTABLE_USER（include/asm-generic/pgalloc.h:8）含 __GFP_DIRECT_RECLAIM，默认 ignore_gfp_reclaim=true 直接放行 → 必须 echo 0 > ignore-gfp-wait（debugfs 属性名沿用老名 "wait"）；
  • 坑 2：页表是单页分配（order-0），默认 min_order=1 意味着 order-0 从不注入 → 必须 echo 0 > min-order。

这两个默认值本意是保护内核关键路径，对通用场景合理，但恰好把页表分配挡在门外——这就是很多"配了 fail_page_alloc 却打不中"悬案的答案。

七、复现工程使用指南（repro/）

7.1 文件与内核要求

  • expand_mremap_leak.c — 复现程序。case 1（默认）：扩张搬移，期望每轮泄漏 delta；case 2（对照）：等长搬移（delta=0），期望零泄漏；
  • setup-fi.sh — root 执行一次，配置 fail_page_alloc（含两个坑的显式覆盖）；
  • run.sh — 编译 + 跑两个 case + 打印 dmesg 注入证据；
  • 内核需 CONFIG_FAULT_INJECTION + CONFIG_FAIL_PAGE_ALLOC + CONFIG_FAULT_INJECTION_DEBUG_FS（检查：zcat /proc/config.gz | grep -E 'FAULT_INJECTION|FAIL_PAGE'）。请在测试 VM 上运行。

7.2 每轮流程（程序自动执行）

读 Committed_AS（before）                    /* /proc/meminfo */
mmap 源 VMA（MAP_PRIVATE|PROT_WRITE|MAP_FIXED，64MB）+ madvise NOHUGEPAGE + 逐页写脏

读 Committed_AS（after）→ round_leak = after - before

expected leak     : 655360 KB (10 rounds x 65536 KB)

*** LEAK CONFIRMED: Committed_AS permanently grew by the charged delta,
    while the process holds NO extra VMA. ***
  • 判据逻辑：程序结束时名下无任何相关 VMA（munmap 干净），Committed_AS 却净增约 N×delta——多出的账无处可归，即泄漏实锤；
  • case 2 对照：等长搬移 delta=0，同样注入失败，Committed_AS 纹丝不动（*** CONTROL OK ***）——证明泄漏唯一来源是 delta 电荷；
  • dmesg 证据：每轮一条 FAULT_INJECTION: forcing a failure，verbose 改 2 可 dump_stack，栈应含 __pte_alloc_one_noprof / __alloc_frozen_pages_noprof；
  • 噪声处理：其他进程的 mmap 会引入波动，信噪比不足时加大信号（-d 256）或独占 VM。

八、修复方案

在 move_vma() 错误分支补一次退账（4 行），DONTUNMAP 除外（全量 charge 由 unmap 对称回冲，退了会双重冲账）：

	err = copy_vma_and_data(vrm, &new_vma);
	if (err && !new_vma)
		return err;

+	/*
+	 * The move failed but the new VMA was established, so we will unmap
+	 * the new VMA below with VMA_ACCOUNT_BIT concealed (to protect the
+	 * source VMA's accounting).  This means the delta pages charged in
+	 * vrm_calc_charge() will never be unaccounted: undo the charge now.
+	 *
+	 * MREMAP_DONTUNMAP is excluded: there we charged the full new_len,
+	 * and unmap_source_vma() does not conceal VMA_ACCOUNT_BIT, so the
+	 * unmap of the new VMA reverts the whole charge symmetrically.
+	 */
+	if (err && !(vrm->flags & MREMAP_DONTUNMAP))
+		vrm_uncharge(vrm);

vrm_uncharge()（mremap.c:1013）内部自带 vma_test(vrm->vma, VMA_ACCOUNT_BIT) 检查——错误路径已把 vrm->vma 换成带标志的 new_vma（mremap.c:1310），条件自然成立。提交时 Fixes 标签指向 1da177e4c3f4。
