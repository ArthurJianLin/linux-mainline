二、核心发现：mremap 扩张搬移错误路径泄漏 Committed_AS 可提交

2.1 缺陷定位 真实逻辑 BUG

位置：mm/mremap.c — move_vma() 错误恢复路径（当前版本约 1383-1407 行）+ unmap_source_vma()（约 1160-1240 行）

引入：1da177e4c3f4（Linux-2.6.12-rc2，2005 年 git 基线）——"Conceal VM_ACCOUNT so old reservation is not undone" 模式从内核有 git 史第一天就存在，潜伏 20 年无人报告。v7.1 的 vrm 重构（b714ccb02a76）平移了同样逻辑。

static unsigned long move_vma(struct vma_remap_struct *vrm)
{
	...
	if (!vrm_calc_charge(vrm))          /* ① 对 delta 页 charge */
		return -ENOMEM;
	...
	err = copy_vma_and_data(vrm, &new_vma);  /* ② 建新 VMA + 搬页表 */
	if (err && !new_vma)
		return err;                 /* copy_vma 失败 → 已 uncharge ✓ */
	...
	if (unlikely(is_dontunmap && !err))
		dontunmap_complete(vrm, new_vma);
	vrm_stat_account(vrm, vrm->new_len);
	if (!is_dontunmap || err)
		unmap_source_vma(vrm);        /* ③ 错误路径下 unmap 新 VMA */
	...
}

2.2 总账推演（缺陷证据链）

Committed_AS 的记账模型：security_vm_enough_memory_mm() 对全局计数器 vm_committed_as 加账；这笔账不挂在任何 VMA 上，只有显式 vm_unacct_memory() 才能减回。

非 DONTUNMAP 扩张搬移（new_len > old_len，私有可写 VMA 带 VMA_ACCOUNT_BIT）的错误路径时序：

  1. vrm_calc_charge()（mremap.c:984-1007）：对 vrm->delta（new_len − old_len）页 charge → vm_committed_as += delta；
  2. copy_vma() 成功建立新 VMA（复制了 VMA_ACCOUNT_BIT）；
  3. move_page_tables() 中途 ENOMEM（moved_len < old_len）→ err = -ENOMEM；
  4. 错误恢复：pmc_revert 把已搬页表移回旧 VMA；vrm->vma = new_vma、vrm->old_len = vrm->new_len、vrm->addr = vrm->new_addr——准备 unmap 新 VMA；
  5. unmap_source_vma()（mremap.c:1179-1202）：accountable_move = vma_test(new_vma, VMA_ACCOUNT_BIT) && !DONTUNMAP = true → 先清除 new_vma 的 VMA_ACCOUNT_BIT 再 unmap → unaccount 0 页。

清位的本意是保护旧 VMA 的账不被错误冲掉（旧 VMA 的 old_len 账必须保留，因为数据已移回、旧 VMA 完整存活）。但副作用是：

最终总账：
  Committed_AS = 旧 VMA 的 old_len（正确保留）
               + delta（① 步 charge，永远无人 uncharge）   <-- 泄漏
  实际存在     = 旧 VMA 的 old_len                          （数据都在）

  → vm_committed_as 永久多记 delta 页

为什么进程退出也救不回来：进程退出时按 VMA 的 VMA_ACCOUNT_BIT 清账，但这笔 delta 是裸账（不挂 VMA）——全局 Committed_AS 膨胀持续到系统重启。在默认 overcommit heuristic（mode 0）下，长期运行的内存受限系统会逐渐拒绝合法的 mmap/MREMAP。

2.3 触发场景与边界

  • 前置条件：MAP_PRIVATE + PROT_WRITE 的 VMA（带 VM_ACCOUNT）；MREMAP 扩张（delta > 0）；非 DONTUNMAP；
  • 触发点：move_page_tables() 中途分配页表失败（ENOMEM）——需要内存压力；或 vma->vm_ops->mremap() 回调失败（同一 err 块，同泄漏）；
  • 对照场景（均已验证不泄漏）：copy_vma() 失败 → 1280 行已调用 vrm_uncharge() ✓；DONTUNMAP 错误路径 → charged = new_len 全量，且 accountable_move=false 不清标志，unmap 新 VMA 时对称回冲 new_len ✓；正常路径 → delta 由新 VMA 的账目自然承接 ✓；
  • 为什么 20 年无人发现：触发需要"扩张搬移 + 页表分配中途失败"的低概率组合，且后果（Committed_AS 偏高）是保守方向的错误——系统只是更早拒绝内存请求，不崩溃、不泄漏真内存，监控上很难归因。

2.4 判重与提交建议

判重：对照 akpm mm-unstable[1]（下载 58492 字节，已核对防 404 落盘）：错误路径结构与本地完全一致，vrm_uncharge() 调用点仅 copy_vma 失败与 mremap_to 两处，无人修复，未撞车。mm-unstable 与本地的 mremap.c 差异均在无关区域（vma_has_anon_rmap 重命名、map_count 检查改进）。

建议修法（在 move_vma() 的 err 处理中、unmap_source_vma() 之前补一次 uncharge）：

	err = copy_vma_and_data(vrm, &new_vma);
	if (err && !new_vma)
		return err;

+	/*
+	 * The move failed but the new VMA was established, so we will unmap
+	 * the new VMA below with VMA_ACCOUNT_BIT concealed (to protect the
+	 * source VMA's accounting).  This means the delta pages charged in
+	 * vrm_calc_charge() will never be unaccounted: undo the charge now
+	 * to avoid a permanent Committed_AS overcount.
+	 *
+	 * MREMAP_DONTUNMAP is excluded: there we charged the full new_len,
+	 * and unmap_source_vma() does not conceal VMA_ACCOUNT_BIT, so the
+	 * unmap of the new VMA reverts the whole charge symmetrically.
+	 */
+	if (err && !(vrm->flags & MREMAP_DONTUNMAP))
+		vrm_uncharge(vrm);

注意 vrm_uncharge() 内部检查 vma_test(vrm->vma, VMA_ACCOUNT_BIT)——此时 vrm->vma 已在错误路径被换成 new_vma（带该标志），检查自然通过，无需改动函数本身。建议 commit message：

Subject: mm/mremap: fix Committed_AS leak when expanding move fails partway

When an expanding (non-MREMAP_DONTUNMAP) move charges the delta pages in
vrm_calc_charge() and then move_page_tables() fails partway (or the
driver's ->mremap callback fails), the error recovery path unmaps the
newly established VMA with VMA_ACCOUNT_BIT concealed to protect the
source VMA's accounting.  The concealed flag means the delta charge is
never unaccounted, so vm_committed_as is permanently overcounted by the
delta - the charge is not tied to any VMA, so it survives even process
exit and only a reboot clears it.

Undo the charge on the error path.  MREMAP_DONTUNMAP is excluded: there
the full new_len charge is reverted symmetrically by unmapping the new
VMA without concealing VMA_ACCOUNT_BIT.

Fixes: 1da177e4c3f4 ("Initial git repository build")
Signed-off-by: <施老师> <邮箱>

三、发现正确但已被上游抢先：call_mmap_prepare() 文件引用泄漏 已撞车

位置：mm/vma.c:2770-2796（本地 v7.3-rc4）。引入：action 机制 ac0a3fc9c07d（2025-10，v7.2）。

缺陷：call_mmap_prepare() 中 vfs_mmap_prepare() 成功后，驱动的 mmap_prepare 钩子可能已替换 desc->vm_file（当前唯一 in-tree 实例：/dev/zero MAP_SHARED → shmem_zero_setup_desc()，新建 shmem file 并持有引用）。此后 call_action_prepare() 失败（remap_pfn_range_prepare() 等 4 种 action prepare 均可真实失败）提前 return——此时 map->file_doesnt_need_get 标志尚未设置（2787 行才设置），abort 路径（2911 行 if (map.file_doesnt_need_get) fput(map.file)）不会 fput 替换后的新文件 → file 引用泄漏。

可达性：当前 in-tree 无"替换 vm_file + 可失败 action"的组合（/dev/zero 不指定 action），但 API 契约缺口真实存在，out-of-tree 驱动或未来驱动可触发。

判重结论：mm-unstable（103431 字节）上该函数已被重构修复——文件替换提前到 action 失败之前，注释明写 /* Update first so file refcount tracked correctly. */，且 file_doesnt_need_get 字段整体删除（还增加了 mmap_prepare_validate() 防御钩子）。不可再提交，但该发现验证了扫描方法论的有效性：上游独立发现了同一缺口并走了更大的重构。

四、三路并行审查结论

4.1 新特性逻辑正确性（vrm 状态机 / dropbehind / swap / interleave / slub）

本周期 9 个 fix 提交逐条验证均完整修复；额外构造的 4 个高价值触发场景全部被内核既有不变量证伪（见第五节证伪表 #1-#4）。结论：本周期新代码逻辑已闭环，无新引入可提交 bug。

4.2 数值 / 边界 / 位运算

对 v7.2..rc4 全量 diff（10808 新增行）按移位/掩码/乘除/min-max/round-align 六类模式筛出 40+ 命中点，逐一定位读完整函数手算排除。唯一存留边界缺陷为 DAMON probe_hits 的 u8 截断（mm/damon/core.c:1349 防护仅覆盖有权重场景，weight=0 的 probe 在 window_len > 255 时 mod 256 回绕）——但引入提交 93508425db11 的 message 明示作者已认知并接受该限制（"Even if it happens, it only degrades the monitoring results"），且该 commit message 引用的函数名本身有笔误，定性为已知设计限制而非可提交 bug，置信度低。

4.3 错误路径资源不对称

对 userfaultfd move/mfill、huge_pmd 迁移、migrate 回滚链、rmap fork、hugetlb dissolve、khugepaged collapse、memcg charge、shmem mfill 计 14 个函数族逐一做资源清单表核对（获取点 → 各错误标签 → 正常路径），全部对称。两个低置信度观察（hugetlb subpool used_hpages 条件覆盖、migrate_vma abort 路径 folio 标志残留）经 2014/2025 年历史追溯与释放路径深挖后均降级为 API 契约/幂等设计，不构成 patch。
