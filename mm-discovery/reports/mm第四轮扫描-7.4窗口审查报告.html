一、第四轮缘起与方法论

1.1 撞车与转向

第三轮我们独立定位的 mremap Committed_AS 泄漏（潜伏 20 年）在发出前被 Lorenzo Stoakes (ARM) 于 10-19 抢先提交进 mm-unstable（b78ed86d8 uncharge 修复 + 4150cd1c0 delta 独立系列），所幸我们的系列尚未外发。教训明确：mremap 领域 Lorenzo 正活跃展开，后续提交必须避开其射程。第四轮矿脉随之转向——无需等 torvalds 出窗口，akpm/mm.git 的 hotfixes 分支就是 7.4 窗口 patch 流的集散地。

1.2 第二轮方法论的复用

  • 重构系列逐条逻辑审查：对声称「No functional change」的重构，逐调用点做旧拒绝集 / 新拒绝集的差分，凡谓词替换必推导布尔等价性，凡依赖不变式必到基准源码核实不变式成立；
  • 修复复审：读上游修复，评估其修法是否完备（错误路径、对称站点、兄弟 bug），从中反向学习 bug 模式；
  • 质量优先：cleanup/doc 类一律归档不行动，只追求真实逻辑缺陷。

审查基准为本地 torvalds 7.3 树（/home/ctyun/桌面/linux-mainline，树 SHA 与 torvalds c03c1a14 逐字节一致），patch 全文经 git.kernel.org cgit /patch/ 端点拉取存档于工作区 .temp/r4/。

二、VMA_SPECIAL_FLAGS 消除系列差分审查

2.1 系列概况

系列名 mm: make VMA flag semantics explicit, eliminate VM_SPECIAL（v6，2026-10-13，Lorenzo Stoakes (ARM)，lore ID 20261013-b4-mmap-prepare-vma-flag-sanify-v6，共 39 patch + cover letter）。动机：VM_SPECIAL 把「是否由核心 mm 管理」「能否扩展/合并」等无关属性搅在一个掩码里，驱动作者长期误用（mlock 滥用 VM_IO 防迁移竞态、uprobes 用 VM_IO 标注内核页映射等）。系列以行为命名的谓词替换掩码，并建立两条强制不变式：mm-managed 映射不得设置 VMA_IO_BIT、不得清除 VMA_MAYWRITE_BIT，经 mmap/mmap_prepare/insert_vm_struct 三处校验强制执行。审阅阵容：Reviewed-by Zi Yan / Suren Baghdasaryan / Gregory Price，Acked-by David Hildenbrand，Cc 覆盖 40+ 子系统维护人。

2.2 谓词链与拒绝集推导

系列分四步引入谓词并逐调用点替换，每一步的拒绝集演变如下（以 7.3 的 VM_SPECIAL = {VM_IO, VM_DONTEXPAND, VM_PFNMAP, VM_MIXEDMAP} 为基准）：

2.3 关键不变式逐点核实

不变式一：hugetlbfs 映射恒同时设置 DONTEXPAND。7.3 源码 fs/hugetlbfs/inode.c:115 vma_set_flags(vma, VMA_HUGETLB_BIT, VMA_DONTEXPAND_BIT)，原子设置。由此旧代码对 hugetlb VMA 实际经 DONTEXPAND ∈ VM_SPECIAL 拒绝合并/折叠/迁移；新代码的显式 hugetlb 排除与旧语义一致——这是 can_merge 最终拒绝集「多出 HUGETLB 却等价」的根基，也是 v6-29（migrate_vma_setup 删除显式 hugetlb 检查）成立的前提。

不变式二：__thp_vma_allowable_orders 的检查从「vm_flags 参数」改为「解引用 vma」无语义漂移。逐一核验 7.3 全部调用点：khugepaged.c:1630/2887/3195（collapse_possible_orders/khugepaged 扫描/MADV_COLLAPSE）与 khugepaged.c:1088/1887 均直接传 vma->vm_flags；madvise.c:187 的 khugepaged_enter_vma 调用发生在 vma->flags = new_vma_flags 提交之后，前瞻 flags 与实际 flags 一致；TVA_PAGEFAULT / TVA_SMAPS 两类调用点被 !in_pf && !smaps 守卫跳过新检查；vma.c:1074/1196/2719 的 vma 合并路径由 can_merge 门禁结构性保证合并双方谓词位一致。旧 VM_NO_KHUGEPAGED = SPECIAL|HUGETLB 与新 !mm_backed || hugetlb 的拒绝集逐位重合。

逐调用点差分汇总（全部 NFC 验证通过）：vma_flags_can_merge、mremap check_prep_vma（DONTEXPAND|PFNMAP → fixed_mapping 恒等）、migrate_vma_setup（261969e17，含 v6-29 的显式 hugetlb 删除先导）、MADV_DODUMP（6ee17eed4）、MADV_DOFORK（e91842c8b）、userfaultfd vma_move_compatible 与 vma_can_userfault 两函数（99c65dc04——旧代码本就有 hugetlb carve-out，方向无翻转）、guard pages is_valid_guard_vma（f67a0ef3c——新代码显式保留 || vma_is_hugetlb(vma)，拒绝集 {SPECIAL}∪{HUGETLB} 逐位一致）。

2.5 深挖验证记录

A. MAYWRITE 清除点审计（29c9a3ce6）。新校验「mm-managed 映射不得清除 VMA_MAYWRITE_BIT」若漏网一个 in-tree 站点即驱动 mmap 直接失败。全树 grep 得 17 个清除站点：RDMA（ionic/hfi1/bnxt_re/mlx5×2）、DRM GEM（vc4/i915/panthor/amdgpu——均经 drm_gem.c:1253 VM_IO|VM_PFNMAP|VM_DONTEXPAND|VM_DONTDUMP 路径）、ptp_vmclock、oradax、pfr_telemetry、ublk、bpf arena。逐一核实全部为非 mm-managed（remap_pfn_range 设 PFNMAP、GEM 设 PFNMAP|IO、arena 由本系列加 MIXEDMAP），其中 ublk 的动机（防守护进程 mprotect 提权写命令缓冲）与校验语义完全互补。无 in-tree 回归。

B. vm_start/vm_end 校验站点审计（912816426）。新校验禁止驱动改动 VMA 边界。全树搜得永久改动者：无。hfi1 与 comedi 均为循环内临时改动后恢复原值；68328fb 的 vm_start 改写位于 #ifndef MMU 的 uClinux 专属路径（nommu 不走该校验）。hfi1 已由本系列另行转换。无 in-tree 回归。

C. mmap hook 后置校验的附带修复（912816426）。__mmap_new_file_vma 错误路径新增 zap_vma + vma_close：修复了驱动在 .mmap 中建立、在 ->close 中释放的状态（如 usbmon ring）在 mmap 失败路径泄漏的问题；vma_close 调用后安装 dummy vm_ops，结构性杜绝 double-close。

D. mmap_prepare 文件引用计数重构（c7f5ccfa5）。逐路径追踪 map->file（mmap 指定）与 map->vm_file（hook 可替换）双轨引用：① prepare 替换文件成功未合并——hook 引用所有权转移给 VMA；② 替换后合并——合并邻 VMA 持有自己的引用，map_put_vm_file 释放多余引用；③ prepare 替换后错误——abort_munmap 路径 map_put_vm_file 释放；④ deprecated .mmap 回调经 vma_set_file 替换（get 新 fput 旧）+ map->vm_file 在 mmap_file 返回后、错误检查前更新——嵌套替换（A→B→C）账目经 vma_set_file 接力后仍然对平；⑤ compat 层 desc->vm_file 引用转移 + 错误路径 fput；⑥ dev_zero 匿名化路径。六路径无泄漏、无双重释放。

E. mlock 迁移竞态重写（392aa5c81）。旧机制以瞬态 VM_IO 阻断迁移双重计数；新机制改用「LOCKONFAULT 置位 + LOCKED 清零」的瞬态组合态（正常状态恒为 LOCKONFAULT ⇒ LOCKED，二者总是同置同清），配合 walk->private 传入 lock 布尔、rmap 侧 try_to_unmap_one/try_to_migrate_one 改查 VMA_LOCKED_MASK 并在 mlock_drain_local 前置检查。瞬态的消费者全数核验：gup.c populate 路径被 vma 写锁串行化（并发 mlock 互斥于 vma_start_write）；smaps 的 "lf" 无 "lg" 瞬态显示与旧 VM_IO 瞬态同级（表象怪异、无语义影响）；trace/mmflags 仅展示。深度竞态形式验证超出本轮范围，未发现设计缺陷。

F. vm_insert_pages 断言修正（e4bb45be7）。旧代码用 VM_WARN_ON_ONCE(mmap_read_trylock(mm)) 断言写锁——trylock 成功（即无人持锁）才告警，持读锁时 trylock 失败反而静默通过，属断言逻辑反转 bug；新代码换 mmap_assert_write_locked()，同时将 PFNMAP 冲突的 BUG_ON 降级为 VM_WARN_ON_ONCE。

3.2.1 truncate 跨界大 folio 数据丢失修复（Zhang Yi · v1 预审，v3 对缝待补）

7.3 基线缺陷形态（已对照本地源码逐点核实）：truncate_inode_pages_range 主循环（truncate.c:437–466）与 shmem_undo_range 均按 folio->index 收集并整只丢弃 in-range folio，对跨界 folio 的唯一保护是 truncate_inode_partial_folio 的布尔返回协议——返回 false 时调用方收缩 start/end 跳过。三条丢失路径：① lend 落于 min_order folio 内部时该 folio 的 index < end，主循环整只丢弃，越界部分的脏数据随缓存静默丢写；② 尾部隔离静默跳过——folio_trylock(folio2) 冲突直接 goto out 且无任何标记，尾 folio 未分裂却被主循环整只吞掉；③ head 侧分裂失败 + 非脏 folio 走整只丢弃（truncate.c:290–293），依赖「非脏⟺有后备」不变式，v1 有意保留。

v1 修复设计（三文件：mm/truncate.c + mm/internal.h 签名 + mm/shmem.c 三个调用点，此前担心的签名不兼容已排除）：输出安全丢弃区间协议——函数改为 truncate_inode_partial_folio(folio, lstart, lend, &pstart, &pend)，pstart = round_up(lstart, min_nrbytes)、pend = round_down(lend+1, min_nrbytes)，跨界 folio 从主循环边界整体排除；tail_isolated 状态机——trylock 冲突或尾部分裂失败时 pend 回拉至 folio2->index，整只跨界尾 folio 保守保留（宁欠勿损）；retry 循环 + 包含性复验——page_folio(split_at2) != folio2 时重取，附带封堵 7.3 的一个并发窗口（try_get 与 trylock 之间并发分裂可令 split_at2 不再属于 folio2，旧代码把外部页传给 folio_split，前置条件违约，潜在误切/VM_BUG 风险）；返回值语义改为「是否发生过分裂」，真实消费者是 shmem.c 主循环的分裂后重扫判定（NULL/NULL 调用），设计自洽。

预审结论：方向正确，几何推演与 folio_split 契约吻合（split_at 所属新 folio 为 order-min_order、其余保持尽量大——head folio 在起始边界切，tail folio 先于 page0 切下首个 min_order 块、再于末边界切）。两条保守取舍均为防丢失方向，无反向风险。v3（-39/+71，4-patch 系列：数据丢失修复 + end-edge 跨界查找 + 边界对齐 + 返回值澄清）相对 v1 的增量待补拉落地后对缝，确认是否处理 v1 保留的整只丢弃路径。

3.2.2 /dev/zero 纯匿名化系列预审（新靶点 d3ed3a4 的修复对象）

Lorenzo 9-08 系列（6 patch）把 MAP_PRIVATE-/dev/zero 从「半匿名特例」改造为真匿名：char-mem.c 移入 mm/、新增 file_is_dev_zero()（f_op 指针判定）、mmap_zero_prepare 不再显式匿名化、core mm 在 call_mmap_prepare 尾部统一转换（map_set_anon：file=NULL、vm_ops=NULL、pgoff=addr>>PAGE_SHIFT）。三处「半匿名」特判（linear_anon_page_index、assert_sane_pgoff、vma_pgoff 文档）全部删除，语义统一收益明确。

核实要点：① 新增 if (!desc->vm_ops) return -EINVAL 检查与 zero 的 MAP_PRIVATE 路径兼容——mm/vma.c:2877 desc 初始化器 .vm_ops = &vma_dummy_vm_ops 非 NULL，先过检查再被转换置空；② 用户可见变化：MAP_PRIVATE-/dev/zero 映射不再出现在 /proc/self/maps 文件列（proc-self-map-files 两个自测改用 /proc/self/exe 印证）；③ merge 自测覆盖相邻合并与 faulted-unfaulted 夹心合并，tools/vma 单测断言 pgoff 重置为匿名语义。

待热修 d3ed3a4 落地对缝的疑点（其标题指向 readonly MAP_SHARED-/dev/zero）：系列中 MAP_SHARED 仍走 shmem_zero_setup_desc 不经转换，问题应集中于 mmap_file() 错误路径语义变化（err || !vma->vm_ops 均置 dummy ops——旧接口驱动置 NULL 的语义被收紧）、call_action_prepare 先于转换执行（action 钩子仍见 /dev/zero file）、只读描述符的 shmem 安装路径三者之一。

其余 8 个修复靶子（swap/uffd/page_alloc/procfs/vmscan/shm/mmap_lock/memory）双通道补拉进行中，落地后逐条回填。locked_vm 双修复（597e4b9/838bb60）的系列上下文已备齐：8-28 的 397432cab17「mm/mremap: account mm->locked_vm correctly for MREMAP_DONTUNMAP」（vrm_stat_account 移序 + dontunmap 分支重构）及九月队列 33-patch 全量 diff 已存档于 .temp/r4/sep-hu/。

五、akpm/mm.git 考古与补拉工程学

本轮补拉横跨数次断流窗口，沉淀出以下可复用的工程结论：

  • 分支结构真相：master 当前为纯主线基底（tip = ff47652a，cifs-fixes-7.3-rc6 合并），mm patch 不在 master 顶端；新 patch 全部住在 mm-hotfixes-stable（已稳定热修）与 mm-hotfixes-unstable（新热修）两个分支。hotfixes-stable 当前仅 7 个新 commit（基线为 09-27 的 mm-stable rollup 被 Linus 合并后的主线），9 个复审靶子在 unstable 分支。
  • SHA 稳定性：hotfixes 分支每日重建，patch 的 mm.git SHA 寿命以小时计（我们 15:01 抓的快照，15:31 时已有 12 个对象被 gc）。任何引用必须记标题而非 SHA；补拉靠「标题匹配新 SHA」或直接走 lore 消息 ID。
  • cgit 四坑：① ?h=master（默认分支）被 301 规范化剥离，curl 必须加 -L 或去掉 h= 参数（非默认分支不受影响）；② n= 分页参数被忽略，每页固定 200 条；③ 页面约 77KB、断流链路 75–120 秒/页，须以 cgit 1.3.1-korg 页脚做完整性校验防截断；④ ?q= 提交搜索在该实例不生效。
  • 镜像生态：GitHub kernelorg-mirror/linux_kernel_git_akpm_mm 的 master 已同步但 mm-* 分支停摆于 9 月——对 10 月新补丁不可用，但九月快照是历史版本的宝库（truncate v1、/dev/zero 原系列、33-patch 热修队列均从中救出）；kernel.googlesource.com 镜像本网络不可达；spinics/mail-archive 均不可用。
  • GitHub API compare 通道（本轮新增）：github.com 网页与 smart-http 断流时 api.github.com 仍稳定；镜像九月快照上的连续提交队列可用 compare/{base}...{tip} + Accept: application/vnd.github.diff 一次请求整体取出（本轮 33-patch 队列 74KB、6-patch 系列 16KB 各一次调用），逐 commit 方案的配额消耗从 ~39 次降至 3 次。
  • 令牌与配额：会话中期 PAT 被吊销（401 Bad credentials，早前推送后已提醒用户 revoke，实际确认已执行）；匿名 API 配额仅 60/小时且出口 IP 为共享 NAT（58.53.165.7），随时被同 IP 流量耗尽——公开仓库数据走无鉴权调用 + compare 批取 + 优先级排序（修复先于系列上下文）是唯一可行姿势。
  • lore Anubis 破解：lore.kernel.org Web 界面被 Anubis v1.26.2 反爬门拦截，但 atom feed 端点豁免；PoW 为 sha256(randomData + str(nonce)) 十六进制前导零（difficulty=4，亚秒可解），提交 pass-challenge 端点换取放行 cookie 后 /raw 全文端点可用。已实现完整求解器（r4-anubis-solve2.py / r4-lore-backfill.py）。
  • 网络窗口学：当日链路呈「通 15–20 分钟 / 断 10–40 分钟」交替（14:34–15:43 长窗口后转短窗），断流期 lore 与 kernel.org 同时不可达（同一路由）。补拉脚本应内置小页面预检 + 页间缓存断点续传 + 内容完整性校验。
  • 两个幽灵 SHA：上一轮枚举出的 bd7eb1f01e 与 d7346a3b0e 不存在于任何已抓取快照（mailmap/日志页均无），恒 404——枚举产物必须落盘可溯源，避免幽灵目标浪费重试预算。
